Purpose

Buttons are the primary trigger for actions in the UI. ClearPath FDO uses three types: Primary for the most important action on a screen, Secondary for supporting actions that need visibility without dominance, and Ghost for low-emphasis actions in toolbars or inline contexts. Every button ships in three sizes (Small, Medium, Large) and five interaction states.

One primary per view
Each screen or modal should have exactly one Primary button. Multiple primary buttons compete for attention and dilute the intended action hierarchy.
Label is always a verb
Button labels must describe the action, not the outcome. Use "Save Appointment" not "Done", "Delete Patient" not "Confirm". Ambiguous labels cause errors.
Size matches context
Large for primary page CTAs. Medium for form actions and dialogs. Small for inline actions, table rows, and dense toolbars. Never mix sizes in the same button group.
Disabled means unavailable
Only disable a button when the action is temporarily blocked. Always pair a disabled button with a visible explanation of why — never leave the user guessing.

Accessibility

All buttons must meet WCAG 2.1 AA standards. The focus ring, keyboard interaction, and screen reader labels are non-negotiable requirements for every button instance.

WCAG Contrast
Minimum 4.5:1 for label text (14px SemiBold).

Primary: white on #27B2B2 — meets AA for large text. Use brand.700 (#104747) where higher contrast is required.

Disabled state is exempt from contrast requirements per WCAG 1.4.3.
Screen Reader
Use native <button> element — never <div> or <a>.

Disabled: add aria-disabled="true" and keep the button focusable so users know it exists.

Icon-only: always add aria-label="[Action]".
Keyboard Navigation
Tab — moves focus to the button.
Enter / Space — activates the button.
Escape — closes any triggered modal or dropdown.

Focus ring: 3px solid brand.300 (#A9E0E0), always visible — never outline:none without a custom ring replacement.
Content & Voice

Button labels follow strict writing rules in a healthcare context. Ambiguous or passive labels increase error rates — every label must be specific, action-first, and under 24 characters.

RuleCorrectIncorrect
Always start with a verb Save Appointment Appointment
Be specific, not generic Delete Patient Confirm
Sentence case only Add new room Add New Room
Max 24 characters Schedule follow-up Click here to schedule a follow-up appointment
No filler words Export report Click to export
Destructive actions name the object Delete appointment Delete
Dos & Don'ts

Following these rules prevents the most common button misuse patterns in healthcare UIs — competing actions, ambiguous labels, and inaccessible disabled states.

Do
  • Use one Primary button per view or modal
  • Start every label with a verb: "Save", "Delete", "Add", "Cancel"
  • Match button size to context — Large for page CTAs, Medium for forms, Small for inline actions
  • Pair a disabled button with a visible explanation of why it is unavailable
  • Use Ghost buttons for low-emphasis secondary actions in toolbars
Don't
  • Place two Primary buttons side by side — use Primary + Secondary instead
  • Use generic labels: "OK", "Done", "Yes", "Submit", "Confirm"
  • Mix button sizes within the same button group
  • Disable a button without showing the user how to unblock the action
  • Use Icon-only buttons without a tooltip — the action must always be discoverable
