Component
Badge
Inline status indicators, type labels, availability signals, and metadata tags.
Purpose

Badges are non-interactive inline visual cues that communicate discrete, scannable information at a glance — status, availability, category, record type, or system counts. They serve a critical trust function in high-density UIs: users must instantly distinguish between states such as Ongoing and Completed without reading full sentences.

Scannable
Colour + label together — never colour alone. Supports users with colour blindness.
Non-interactive
Chips communicate state. Never clickable unless wrapped in a button or filter control.
Context-bound
Status, appointment type, and availability are separate token systems — do not mix them.
Clinical Trust
Labels use approved vocabulary only. No invented statuses or repurposed colours.
Dos & Don'ts
Do
  • Always pair a colour fill with a visible text label — never rely on colour alone.
  • Use status chips exclusively for appointment lifecycle states.
  • Use type tags only on cards, detail panels, and booking flows.
  • Keep labels short (1–2 words). Use approved vocabulary: Ongoing · Completed · Cancelled · Future · Pending · Upcoming.
  • Use the pulse dot only on the Ongoing chip — it signals a live, time-sensitive state.
Don't
  • Don't use appointment type colours for status — they are separate systems with different semantics.
  • Don't stack multiple chips of the same category on a single element.
  • Don't invent new status colours ad-hoc — flag as a New Token Candidate first.
  • Don't use red or green outside their defined semantic meaning (error vs. success).
  • Don't apply the pulse animation outside Ongoing or Live contexts — it implies urgency.
Variants

Chip variants are defined by three independent axes — never by specific UI labels like "Ongoing" or "Medical Test". This keeps the design system decoupled from application data (Atlassian/Carbon pattern). Combine one intent + one appearance style + any structural modifiers to build any chip.

Status Chips

Use the .chip base class with a variant modifier. Never use colour alone — always include a visible label.

<!-- Ongoing → chip-danger: pulse dot required -->
<span class="chip chip-danger"><span class="pulse-dot"></span> Ongoing</span>

<!-- Completed → chip-success: check icon (ti-check) -->
<span class="chip chip-success">
  <i class="ti ti-check" style="font-size:12px;"></i> Completed
</span>

<!-- Cancelled → chip-neutral: no icon -->
<span class="chip chip-neutral">Cancelled</span>

<!-- Future → chip-brand: dashed border applied via CSS -->

Display Logic

Derive the display status at render time — never pass backend status directly to the chip class.

// Derive chip intent from appointment data
// Returns the CSS class intent: danger · success · warning · info · brand · neutral
function getChipIntent(appointment) {
  const now  = new Date();
  const date = new Date(appointment.date);
  const isToday = date.toDateString() === now.toDateString();
  const isPast  = date < now;

  if (isPast && ['due','pending'].includes(appointment.status)) return 'neutral';  // Cancelled
  if (isToday && isWithin1Hour(appointment))                    return 'danger';   // Ongoing
  if (appointment.status === 'completed')                        return 'success';  // Completed
  if (appointment.status === 'pending')                          return 'warning';  // Pending
  if (appointment.status === 'upcoming')                         return 'info';     // Upcoming
  if (!isPast)                                                   return 'brand';    // Future
  return 'neutral';
}

// Usage: <span class="chip chip-${getChipIntent(appt)}">...</span>
