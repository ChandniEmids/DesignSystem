The Big Picture
What this tool is, why it exists, and the business problem it solves
One-line summary
Surescripts is the Health Information Network (HIN) that routes all electronic prescriptions across the US. Before any system can connect to it, that system must certify — prove it speaks the NCPDP standard correctly. The Certification Tester is the tool that runs those proofs.

The recurring problem

NCPDP updates its standard every 5–7 years. Every update means every single customer — EHRs, pharmacies, PBMs — must update their integration code and re-certify. Hundreds of customers all at once. This created a predictable, massive workload crisis. The Certification Tester was built to absorb it.

57 hrs
Before the tool
Fully manual. Surescripts staff guided every certification run.
18 hrs
After v1 launched
Self-service tool. Customers run tests independently.
9 hrs
Target — end of 2026
Ongoing UX work + automation. This is the design team's goal.
Design context
This is not a one-time project. The NCPDP upgrade cycle means this problem recurs every 5–7 years at scale. Design decisions made now affect hundreds of customers across multiple certification cycles. The initiative is called Onboarding Modernization.

Message Formats
Two distinct NCPDP message formats — different jobs, different structures
SCRIPT (XML)
e-Prescribing

Rich, structured, verbose XML format. Used for all prescription transactions between prescribers, EHRs, pharmacies, and Surescripts.

Simple analogy
"Doctor sends the prescription to the pharmacy."
Transaction types
NewRx CancelRx Renewal Request Transfer
Telecom D.0
Claims / Billing

Compact string format. Used for pharmacy claims billing and adjudication — the insurance side after the prescription is received.

Simple analogy
"Pharmacy bills the insurance and gets the copay/approval."

Claims billing Eligibility checks Copay adjudication

What Gets Certified
Why certification is mandatory, what it proves, and what it's actually tied to
Key mental model
"We don't certify people. We certify customer systems for specific products and message types."

Why certification is mandatory

Healthcare standards are mandated by CMS, ONC, payers, and PBMs. Before a system can send e-prescriptions, submit pharmacy claims, or exchange prior authorizations — it must prove it:

Sends messages in the correct format
Handles error cases correctly
Follows NCPDP rules exactly
This is machine-to-machine testing — not human training. No clinicians involved.

What certification is tied to

Customer AccountThe organisation
Application NameThe specific system being certified
Application VersionChanging version may require re-cert
Certified Product(s)e.g. ePrescribing, Eligibility, RTPB
Message Typese.g. NewRx, CancelRx, RenewalRequest
Date of certificationLogged for compliance records
Note: Adding new products or message types requires additional certification runs.

Who is NOT the certification target

Clinicians
End users of the EHR
The person running the tests
The customer's application / system

The Tool: Workbench
Platform overview, the two main UI areas, and the environment pipeline
Platform
All certification work lives on a platform called Workbench. It has two distinct UI areas — one for customer teams, one for internal Surescripts teams. These are separate spaces with different permissions and different jobs.
Certification Tester
External Users

Where customer teams (EHRs, pharmacies, PBMs) log in and execute their certification test runs. They see only their own projects.

Customers execute tests here. They cannot create or edit test content.
Test Manager
Internal — Surescripts

Where Surescripts certification teams build test cases, manage assertions, review customer submissions, and approve or reject certification runs.

Surescripts defines, manages, and approves certification here.

Environment pipeline

Devint
Dev / integration. Internal only.
Stage
Customer certification testing. Real messages, real systems.
Production
Live. Customer reaches here after successful certification.
Design note: Customers test in Stage — unusual in the industry. Most companies don't expose staging to external users. Surescripts does this deliberately to enable realistic self-service testing with real message flows.

Linking messages: Message ID and Relate To

Every outbound message has a unique Message ID. When a response step references that original message, it uses a Relate To field containing that ID. This links the request and response together for validation.

Step 1: Customer sends NewRx → Message ID = "MSG-001"
Step 2: Customer receives Response → Relate To = "MSG-001"

Assertions
The pass/fail gatekeepers — understanding these is core to understanding the tool
Definition
An assertion is a specific yes/no rule that verifies one expected condition during a test. If it fails, the test step fails — regardless of whether everything else passed. Assertions are deliberately granular so failures are pinpointed, not vague.

By source

System assertions
Built in by Surescripts. Always present. Cannot be removed or bypassed.
User-defined assertions
Added manually by a Test Manager admin for specific or custom requirements.

By severity

Error Blocks progress
Message fails. Customer must fix and resend. Cannot proceed past this step.
Warning Non-blocking
Execution continues. Warning is flagged and customer is informed, but not stopped.

What assertions validate

Required fields present
Field values match expected
Message structure is correct
Error handling as expected
Correct response type returned
Business rules followed

How failures roll up to certification

Assertion fails
Step fails
Case fails
Certification blocked
The passport analogy
Passport valid? ✅   Ticket valid? ✅   Name matches? ❌ → You don't board the flight.

A system can be "mostly working" — message sent, workflow runs to completion — and still fail certification because one required field was missing or one value was the wrong format. There is no partial credit at the certification level.

End-to-End: One Message Through a Test Step
What actually happens when a customer sends a message — using NewRx as the example. Same pattern applies to all message types.
1
Test step is activated
The external customer user opens the step in Certification Tester, reads the instructions, and sees what message to send. No validation happens yet — the tool is waiting.
2
Customer system sends the message
The customer's actual system sends a NewRx XML message into the Stage environment. This is a real outbound message — it is not typed into the UI. It comes from their live integration code.
3
Message is captured and displayed
The tool detects the message and displays it. The user confirms it to associate it with the active test step. At this point, the tool knows: "this is the message to validate."
4
Assertions execute against the message
Each assertion runs independently — checking message type, required fields, content validity, message ID references, business rule compliance. Each returns pass or fail on its own.
5
Step result is calculated
All required assertions must pass. One failure = step fails, even if everything else passed. The UI shows exactly which assertion failed, why it failed, and which field caused it.
6
Results roll up through the hierarchy
Step result feeds into the Test Case, which feeds into the Project, which determines the overall certification status. Until this step passes, the test case cannot pass.
7
Fix and re-execute
Customer fixes the issue in their integration code, sends a corrected message, and re-executes the same step. Assertions run again. Real-time feedback — no waiting for a Surescripts person to manually review.
All assertions pass — step complete
Move to the next step. Repeat until all required test cases are complete. Then certification can proceed.

The Certification Journey
End-to-end flow from the customer tester's point of view — login to certified
Real-world example
Role: External customer tester at an EHR company  ·  Goal: Get e-Prescribing certified  ·  Test: QA eRX / Prescriber / Fernandez / Amoxicillin — covering NewRx, Change, Refill, and Cancel transactions
Core rule: The customer tester never creates tests. Their only job is to:  Execute  ·  Attest  ·  Submit  ·  Respond to review feedback

The 4 phases at a glance

Phase 1
Access & Readiness
Log in, check dashboard, complete Test Data Setup if required
Phase 2
Test Execution
Execute test cases step by step, attest results, mark pass or fail
Phase 3
Submission & Review
Submit the project for review — project locks while a Surescripts reviewer evaluates
Phase 4
Outcome
Approved → certified. Changes required → fix and resubmit

Full flow diagram

Surescripts Certification Journey — End User Flow  ·  4 phases  ·  28 steps
1

Phase 1 — Access & Readiness

1
Log in to Certification Tool
Customer accesses Workbench using their account credentials.
2
Certification Dashboard loads
All assigned test projects are visible. The user sees their progress at a glance — no access to Test Manager or other accounts.
3
Decision: Test Data Setup required?
Some certification runs require pre-test data to be submitted before execution can begin. If not required, skip to step 6.
4
Complete Test Data Setup
User fills and submits the required forms. This data is reviewed by Surescripts before the project can proceed.
5
Decision: Data approved?
If rejected, user revises and resubmits. Loop continues until approved.
6
Return to Dashboard — ready to execute
All setup complete. The user can now open their project and begin test execution.
2

Phase 2 — Test Execution

7
Open Certification Project
User selects the assigned project from the dashboard to see all test cases inside it.
8
Select a Test Case
e.g. "Fernandez / Amoxicillin — NewRx". Each test case contains multiple test steps to be executed in order.
9
Decision: Status = "Update Requires Restart"?
If the test case content was updated after execution began, the tool flags it. User must restart before continuing.
10
Restart Test Case (if required)
Resets execution state. User returns to step 8 and selects the case again to begin fresh.
11
Start Test Execution
User initiates execution for the test case. Each step is now presented in sequence.
12
Read Test Step Instructions
Instructions written by the Test Manager admin tell the user exactly what message to send (e.g. "Send a NewRx for patient Fernandez with drug Amoxicillin 500mg").
13
Perform action in own system
User triggers the transaction from their own EHR or pharmacy system — not typed into the tool. The tool receives it on the other end and validates it.
14
Decision: System assertion auto-passes?
All automated validation rules run instantly. If they all pass, the system marks the step as auto-passed and the user moves to attestation. If any fail, validation errors are shown.
15
Review validation errors (if auto-pass fails)
Tool shows exactly which assertion failed and why — e.g. "Required field DEA number missing". User fixes their system and resends.
16
User Attestation
User manually confirms via checkbox that they have reviewed the result and accept it as accurate.
What is User Attestation?
System auto-pass
Technical checks passed automatically. All assertions validated by the tool.
User Attestation
Human sign-off. The user confirms they've reviewed the result and accepts responsibility for its accuracy. Required for compliance and audit.
Even when a step auto-passes, attestation is still required. A technical pass alone is not sufficient for certification — a human must acknowledge the outcome.
17
Decision: Did the step pass?
If yes → mark step passed and move on. If no → add failure comments and evidence before proceeding.
18
Add failure comments & evidence
Required when a step fails. User documents what went wrong and attaches any supporting files. Reviewer will use this during evaluation.
19
Mark Step Passed
Step is complete. Result rolls up: step → test case → project → certification status.
20
Repeat for all remaining steps
Steps 12–19 repeat for each test step in the case. Once all steps are done, the test case execution is complete.
3

Phase 3 — Submission & Review

21
Complete Test Case Execution
All steps in the test case are done. User repeats steps 8–20 for each remaining test case in the project.
22
Download Execution Report (optional)
User can download a full report of all test case results before submitting — useful for internal review or records.
23
Submit Project for Review
User submits the entire project. The project is now locked — no further edits possible until the reviewer returns a decision.
24
Reviewer evaluates results
A Surescripts Test Reviewer inspects all execution results, comments, and evidence. They will either approve or request changes.
4

Phase 4 — Outcome

Approved
Certification is complete. The customer's application is now certified for the tested product and message types. They can connect to the production environment.
Changes Required
Project is unlocked. User fixes the flagged issues, re-executes the failed test cases, and resubmits from step 8. The cycle repeats until approved.
